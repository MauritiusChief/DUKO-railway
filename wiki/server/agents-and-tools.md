# Agents 与工具

## 通用执行模型

所有当前 Agent 继承 `BaseAgent`。基类负责多轮 LLM 调用、流式文本、工具调用、搜索预算、最大轮数、工具结果回填及可选 trace。预算耗尽后会移除受预算限制的工具，但清单或布局编辑等非搜索工具仍可继续使用。

工具调用是否并发由 Agent 显式决定。表格解析和布局 Agent 允许同一轮的委派工具并行；会修改共享清单或布局的工具保持串行，避免状态竞争。

## 主 Agent

### ChatAgent

面向多轮产品问答和当前清单修改。它可以按形状、描述或结构化条件搜索 SKU，读取和增删改解析清单，查询产品库存与组件，读取生成后的产品列表，并累积用户笔记。清单是单次请求上下文中的可变对象；路由按请求传入历史，而不是让 Agent 自身维护永久会话。

### TableParseAgent

把原始清单文本转换为结构化项目。它可并行委派批量搜索、单项精确搜索和玻璃门数量计算，也能直接搜索补漏、编辑 manifest、查询组件。解析完成后由代码计算暴露状态并将结果保存为用户历史。它是单请求流程，不负责产品清单后续编辑或笔记写入。

### ImageParseAgent

使用 OpenRouter 多模态 provider 读取一张或多张 base64/data URL 图片，并用形状和描述搜索验证识别结果。其输出是文本，通常再交给表格解析流程结构化。图片清晰度、模型视觉能力和 20 MB 请求体上限都是实际约束。

### LayoutAgent 与 LayoutOcrAgent

布局流程先由无工具的视觉 OCR Agent 提取图像信息，再由文本 LayoutAgent 读取和修改布局。布局工具支持墙体、岛台连接关系和项目的创建、删除、插入、定位及属性更新；修改后可实时推送布局快照。文本 Agent发现歧义时可再次委派视觉 OCR，并可委派批量或精确 SKU 搜索。最终物料清单另由确定性算法生成，不依赖 LLM 端点。

## 搜索子 Agent

- `BatchSearchAgent`：每批最多 10 项，组合使用形状编辑距离、BM25 描述和两者交集搜索，返回最佳及备选候选。
- `PreciseSearchAgent`：一次处理一项，使用结构化过滤树组合形状、描述、向量和颜色条件。
- `GlassDoorAgent`：查询橱柜记录的描述字段，由模型理解门数并按数量汇总；自然语言描述缺失时不能保证得出门数。
- `LayoutOcrAgent`：只做视觉读取，不拥有工具；可作为布局主流程的初次或二次 OCR。

## 工具领域

搜索工具：

- 形状代码和尺寸代码编辑距离匹配，可带颜色过滤。
- 基于 MiniSearch 的 BM25 描述检索。
- 形状与描述结果交集。
- 结构化多维搜索，将布尔过滤树、BM25、形状匹配和 LanceDB 向量候选组合。

状态工具：

- manifest 的读取、增加、删除和单元格编辑。
- layout 的读取以及墙体、项目、连接关系编辑。
- 产品库存、产品组件和生成产品列表查询。
- 请求上下文中的笔记累积。

委派工具不是远程队列。它们在当前 server 请求内创建子 Agent，共用 provider，并受各自预算和轮数限制。子 Agent trace 会以父工具调用 ID 关联，但只有 `TRACE_LOG=true` 时写库。

## 模型配置边界

当前 provider 默认值写在 `server/src/llm/provider.ts`：文本模型使用 DeepSeek 默认配置，多模态模型使用 OpenRouter 默认配置。代码只从环境读取 `DEEPSEEK_API_KEY` 和 `OPENROUTER_API_KEY`；`server/.env.example` 中的 `OPENROUTER_MODEL` 当前未被读取，设置它不会覆盖模型。

`CHAT_LOG` 可写 Markdown 调试日志，`TRACE_LOG` 可将系统消息、用户内容、工具 schema、工具参数/结果和模型回复写入 SQLite。生产开启前应把这些内容视为敏感业务数据，并落实访问与保留策略。

## 能力边界

- 搜索质量取决于当前导入的 CSV、SQLite、BM25 和 LanceDB 是否同版本。
- 本地向量生成首次可能从 Hugging Face 下载约 23 MB 模型；并非完全无网络初始化。
- 工具验证降低但不能消除 LLM 幻觉。尤其是 OCR、自然语言门数判断和候选取舍仍需人工复核。
- Agent 编排随 HTTP 请求执行，没有独立持久作业队列；server 重启会中断正在进行的 LLM 请求。
